========================================================================
BUGSAFARI THESIS DEFENSE STUDY GUIDE
TOPIC: SOFTWARE REQUIREMENTS
========================================================================

--------------------------------------------------------------------
1. WHAT IT REPRESENTS
--------------------------------------------------------------------
The software requirements list everything needed to BUILD, RUN and DEPLOY
BugSafari. The version numbers are the ones the project actually declares
in its package files, not general recommendations. The list is split into
three parts: what a developer needs on their own machine, what the server
needs, and the outside services the system talks to.


--------------------------------------------------------------------
2. PURPOSE AND IMPORTANCE IN BUGSAFARI
--------------------------------------------------------------------
Requirements make the system reproducible. Anyone should be able to take
this list, set up the same tools at the same versions, and get an
identical build. It also states clearly which services are mandatory and
which are optional, so the system degrades gracefully when an optional
service is missing.


--------------------------------------------------------------------
3. DEVELOPMENT MACHINE
--------------------------------------------------------------------
  Operating system  - Windows 10/11, macOS 12+, or a recent Linux.
                      Development is done on Windows in this project.
  Node.js           - ^20.19.0 or >=22.12.0. Older versions will not
                      build.
  npm               - Version 10 or later. The project uses npm
                      workspaces, so a single install at the root covers
                      all three packages.
  Git               - Any recent version.
  Code editor       - Visual Studio Code recommended (ships TypeScript
                      settings the editor picks up).
  Web browser       - Chrome, Edge or Firefox, current version, to open
                      the dashboard at localhost:5173.
  Database access   - A free MongoDB Atlas account. There is no local
                      MongoDB container; the connection string points at
                      Atlas.

--------------------------------------------------------------------
6. SERVER DEPLOYMENT
--------------------------------------------------------------------
  Operating system  - Ubuntu 22.04 or similar Linux. Target is a
                      DigitalOcean droplet.
  Container runtime - Podman or Docker with compose support. Two compose
                      files exist: one local, one production.
  Base image        - mcr.microsoft.com/playwright:v1.60.0-jammy. Ships
                      Chromium and all its system libraries already
                      installed, which is why it is used instead of a
                      plain Node image.
  Redis             - redis:alpine, latest stable. Holds the run queue and
                      the cross-process event bridge.
  Reverse proxy     - Caddy, latest stable. Handles HTTPS certificates and
                      forwards traffic to port 3000.
  Database          - MongoDB Atlas, managed, not run in a container.
  Frontend hosting  - Any static host; Vercel is used here. The dashboard
                      builds to plain files, so it does not need a Node
                      server.


--------------------------------------------------------------------
7. EXTERNAL SERVICES (WHAT HAPPENS WITHOUT EACH)
--------------------------------------------------------------------
  MongoDB Atlas     - Required. Without it nothing can be saved. Runs
                      still work but no history is kept.
  Google Gemini API - Optional. Without it the system answers fix requests
                      from a built-in catalog of known bug types instead.
                      Everything else is unaffected.
  SMTP mail server  - Optional. Without it password reset email cannot be
                      delivered. All other account features still work.
  Redis             - Only for concurrent runs. Without it the API runs
                      the test in its own process, one at a time.


--------------------------------------------------------------------
8. PORTS
--------------------------------------------------------------------
  5173      - The dashboard development server
  3000      - The REST API and the live stream, both on the same port
  6379      - Redis
  27017     - MongoDB, when a local instance is used instead of Atlas
  80 / 443  - The reverse proxy in production


--------------------------------------------------------------------
9. CONFIGURATION
--------------------------------------------------------------------
Settings are read from environment files rather than hard coded. The ones
that MUST be set are: the MongoDB connection string, the secret used to
sign tokens, and the key used to encrypt any credentials the tester
supplies for a site that needs a login. The rest, including the AI and
email settings, the step and timeout limits, and the worker count, have
working defaults.


--------------------------------------------------------------------
10. TESTING AND BUILD TOOLS
--------------------------------------------------------------------
Tests are written as plain TypeScript files that assert with Node's own
"assert" module and are run by a small script in each package. There is no
test framework to install. Playwright's own test runner is available for
browser-level tests, and ESLint checks the dashboard code.


--------------------------------------------------------------------
11. WHY THESE CHOICES WERE MADE
--------------------------------------------------------------------
  * The Playwright base image is chosen over a plain Node image because it
    already ships Chromium and its system libraries, avoiding fragile
    manual browser installs in the container.
  * Optional services (Gemini, SMTP, Redis) each have a graceful fallback,
    so the core testing feature never depends on a paid or extra service.
  * npm workspaces let a single root install cover all three packages,
    keeping setup simple.
  * A static frontend host (Vercel) is enough because the dashboard builds
    to plain files and needs no Node server.


--------------------------------------------------------------------
12. POSSIBLE DEFENSE QUESTIONS AND SUGGESTED ANSWERS
--------------------------------------------------------------------
Q: Which services are mandatory and which are optional?
A: Only MongoDB Atlas is mandatory for saving history. Gemini, SMTP and
   Redis are optional, each with a fallback: a built-in fix catalog, no
   reset email, and single-process one-at-a-time runs respectively.

Q: Why use the Playwright container image instead of a plain Node image?
A: It ships Chromium and all its system libraries pre-installed, so the
   browser the engine drives works in the container without a fragile
   manual install.

Q: Why Podman/Docker rather than installing everything on the host?
A: Containers make the deployment reproducible and match the local setup.
   Two compose files (local and production) keep the two environments in
   line.

Q: What must be configured before the system will run?
A: The MongoDB connection string, the token-signing secret, and the
   encryption key for any site credentials the tester supplies. Everything
   else has a working default.

Q: What testing approach does the project use?
A: Plain TypeScript files asserting with Node's assert module, run by a
   small per-package script. No heavy framework. Playwright's runner is
   available for browser-level tests and ESLint checks the dashboard.

Q: Why does the API and the live stream share port 3000?
A: The REST API (Express) and the Socket.IO stream run on the same server
   process and port, simplifying deployment behind the reverse proxy.

Q: How does the system scale to many concurrent testers?
A: With Redis and BullMQ, run requests are queued and executed in separate
   worker processes, one run per worker. Without Redis it falls back to
   one run at a time in the API process.
