# 3.x API Specifications and Interface Architecture

The BugSafari platform is realised as a distributed system whose behaviour emerges from the disciplined interaction of three cooperating tiers: the Watchtower Dashboard, which serves as the human operator console; the Testing Core Engine, which houses the autonomous exploration intelligence and its attack arsenal; and a constellation of external services that supply cognitive reasoning, browser instrumentation, and transactional messaging. Because these tiers execute in separate processes and, in deployment, on separate hosts, the coherence of the system depends entirely on the clarity and rigour of the interfaces that bind them. This section specifies those interfaces as an architectural contract, describing the communication protocols, the security mechanisms that protect them, and the interaction patterns through which the tiers exchange intent and observation. The specification is deliberately protocol-oriented rather than implementation-oriented: it defines what each interface guarantees and how the parties negotiate state, independent of the concrete handlers that fulfil those guarantees.

Three distinct interface styles are employed, each selected to match a different communication semantics. Request–response transactions that mutate durable state or retrieve authoritative records are conducted over a stateless HTTP gateway. Continuous, low-latency exchange of telemetry, sensory imagery, and control intent is conducted over a persistent bidirectional streaming channel. Delegated computation and instrumentation are conducted through integrations with external systems over secured application protocols. The remainder of this section treats each style in turn.

## 3.x.1 RESTful HTTP Gateway Specification

The primary transactional boundary between the Watchtower Dashboard and the Testing Core Engine is a RESTful HTTP gateway. The architecture adopts the Representational State Transfer model because its resource-oriented discipline aligns naturally with the platform's domain: operator accounts, exploration sessions, forensic findings, and configuration artefacts are all long-lived resources whose lifecycle is naturally expressed through the uniform verbs of the HTTP protocol. Each resource is addressed as a noun and manipulated through a constrained set of actions, which yields an interface that is predictable, self-describing, and amenable to independent evolution of client and server.

All gateway traffic is conducted over HTTPS. Transport Layer Security is treated as a non-negotiable substrate rather than an optional hardening measure, because the gateway conveys authentication credentials, bearer tokens, and potentially sensitive forensic data describing the behaviour of the systems under test. Encrypting the channel in transit protects both the confidentiality of these payloads and the integrity of the messages against tampering by intermediaries.

The data interchange format across the gateway is JSON. This choice reflects the platform's commitment to a strictly typed contract shared between the frontend and backend tiers: the same structural definitions that govern the serialised messages on the wire also govern the compile-time types on either side of the boundary, so that the shape of a request or response is validated statically during development and consistently interpreted at runtime. JSON is favoured for its ubiquity, its native affinity with the JavaScript runtime of both tiers, and its human readability, which materially aids diagnosis during exploratory testing runs.

Authentication is founded on the JSON Web Token. Upon successful presentation of credentials, the gateway issues a signed token that encodes the authenticated operator's identity and the claims that describe their authorised scope. Thereafter, the client presents this token on each protected request as a bearer credential. The signature over the token permits the server to verify authenticity and integrity by local cryptographic parsing alone, without consulting a server-side session store. This design yields a stateless authorisation model in which any instance of the Testing Core Engine can independently validate a request, a property that is essential to horizontal scalability and to the clean separation between authentication and the resources being protected. The architecture further accommodates an unauthenticated guest posture: requests bearing no token are admitted to a constrained capability set that permits active exploration of a target application while categorically denying persistence of results to the multi-tenant datastore, thereby enforcing the principle of least privilege at the level of the authorisation model itself.

Credential secrecy at rest is protected through adaptive password hashing using the bcrypt function. Operator passwords are never stored or transmitted in a recoverable form; instead, a salted hash is computed with a deliberately high computational cost factor and only the resulting digest is retained. The salt defeats precomputation attacks, and the tunable work factor allows the cost of verification to be raised over time to track advances in adversarial hardware. Verification consists of recomputing the digest of a presented credential and comparing it against the stored value, so that the plaintext is required only transiently during authentication and is never persisted.

Authorisation is applied as a distinct concern layered above authentication. Once a token is validated, the claims it carries determine which resources the caller may address and which actions they may perform, and multi-tenant isolation ensures that an operator's queries are scoped exclusively to records they own. This separation ensures that the question of who the caller is remains cleanly decoupled from the question of what the caller may do.

The gateway communicates outcomes through the standardised semantics of HTTP status codes. Successful retrievals, creations, and mutations are signalled with the appropriate success codes; malformed or semantically invalid requests, failed authentication, insufficient authorisation, and absent resources are each signalled with the status code that precisely denotes that condition. Error responses carry a structured JSON body that conveys a machine-interpretable description of the fault alongside human-readable context, enabling the Watchtower Dashboard to render meaningful diagnostics and to distinguish deterministically between conditions that warrant retry, re-authentication, or operator correction. This uniform and predictable error surface is itself part of the interface contract, ensuring that failure is communicated with the same rigour as success.

## 3.x.2 Real-Time Bidirectional Streaming Specification

The transactional gateway is ill-suited to the platform's most distinctive requirement: the continuous, live projection of the autonomous engine's activity into the operator's console. Exploratory testing generates a dense, unbounded stream of events — element interaction decisions, machine-learning target ratings, sensory frame captures, and unhandled fault reports — that must reach the operator with minimal latency and without the overhead of repeated polling. To satisfy this requirement the architecture establishes a persistent, full-duplex streaming channel between the Watchtower Dashboard and the Testing Core Engine, realised through the WebSocket protocol as orchestrated by a Socket.IO abstraction layered above it.

The choice of a WebSocket foundation is dictated by the bidirectional and asymmetric nature of the exchange. The engine must push a high-frequency outbound stream of observations to the operator, while the operator must retain the ability to inject inbound control intent at any moment. A single long-lived connection carrying traffic in both directions satisfies this far more economically than any request–response arrangement, eliminating per-message connection overhead and enabling true server-initiated delivery. The Socket.IO orchestration layer is adopted above the raw protocol because it furnishes the connection-management guarantees the platform requires — automatic transport negotiation, resilient reconnection, and logical multiplexing of distinct event streams over one physical connection.

The connection lifecycle is explicitly managed. A session begins with a negotiation handshake during which the operator's identity and authorisation are established, so that the streaming channel is subject to the same access-control discipline as the transactional gateway and telemetry is never delivered to an unauthenticated or unauthorised observer. Once established, the connection is maintained by a heartbeat mechanism in which lightweight liveness probes are exchanged at regular intervals. The heartbeat serves two purposes: it allows either party to detect promptly when the peer or the intervening network has failed, and it keeps the connection active across intermediaries that would otherwise reclaim an idle channel. Should the connection be lost, an automatic reconnection mechanism re-establishes it, progressively backing off between attempts to avoid overwhelming a recovering endpoint, and re-negotiating authorisation upon restoration so that continuity of the operator's view is recovered without compromising the security posture of the channel.

Communication over the channel follows a publish–subscribe model rather than direct point-to-point addressing. The engine publishes events to named logical channels according to their kind, and the dashboard subscribes to those channels relevant to the operator's current focus. Three principal categories of event traverse the channel. The first is telemetry: the engine's running narrative of its own cognition, comprising the elements it elects to interact with, the numeric ratings its scoring model assigns to candidate targets, and the lifecycle transitions of the exploration run. The second is browser frame streaming: a sequence of sensory captures of the application under test, delivered as a live visual feed that allows the operator to witness the engine's perspective in real time. The third is real-time control: inbound commands through which the operator steers the run — initiating, pausing, resuming, or terminating exploration — which the engine consumes and acts upon promptly. Segregating these categories onto distinct logical channels allows each to be subscribed to, filtered, and reasoned about independently, and decouples the producers of events from their consumers so that either side may evolve its handling of a stream without disturbing the other.

This streaming architecture is what renders the Watchtower a genuine observability surface rather than a periodic reporting tool. By projecting the engine's decisions, perceptions, and faults into the operator's view as they occur, and by accepting control intent along the same channel, it closes the loop between autonomous execution and human oversight in real time.

## 3.x.3 External Systems Integration Specification

Beyond the interfaces internal to the platform, the Testing Core Engine depends upon several external systems to fulfil capabilities that lie outside its own domain. Each such dependency is expressed as a well-defined integration governed by a secured application protocol, so that the engine's core logic remains insulated from the particulars of the external provider and interacts with it only through a stable, bounded contract.

The first integration furnishes the engine's cognitive faculty. To reason about the semantics of an application's interface — to interpret the meaning of elements and to inform the heuristics that guide exploration — the engine delegates to an external large-language-model service, the Google Gemini platform. This integration is conducted over HTTPS, so that the prompts describing the observed application state and the responses conveying the model's inferences are encrypted in transit. The engine treats the service as a request–response oracle: it submits a structured description of the situation requiring judgement and consumes the model's response, incorporating that judgement into its own decision process. Delegating semantic reasoning to a specialised external model allows the engine to benefit from cognitive capability far exceeding what could be embedded locally, while the HTTPS boundary and the structured contract confine the dependency to a single, replaceable seam in the architecture.

The second integration provides the engine's sensory and motor apparatus: its capacity to perceive and to act upon a live web application. This is achieved through a browser-automation layer built upon the Playwright framework, which in turn drives a real browser instance through the Chrome DevTools Protocol. The DevTools Protocol constitutes a low-level command and event interface into the browser itself, granting the engine the fidelity of control it requires — the ability to traverse the document object model, to synthesise user interactions, to capture the rendered visual state that feeds the frame stream, and to observe faults and network activity at the level of the browser's own instrumentation. Playwright supplies a coherent programmatic abstraction over this protocol, and the engine issues its exploratory actions and receives its perceptions through that abstraction. This layer is the physical substrate of the platform's autonomy: it is the conduit through which the abstract decisions of the scoring and navigation intelligence are translated into concrete interactions with the application under test, and through which the consequences of those interactions are observed and returned.

The third integration serves the platform's account-lifecycle communications. Transactional electronic mail — the messages that verify a newly registered operator's address and that mediate recovery of access to an existing account — is dispatched through an external mail-transfer service using the Simple Mail Transfer Protocol. The engine composes the appropriate message, bearing a single-use verification or recovery artefact, and hands it to the mail service for delivery over a secured SMTP session. Routing these communications through a dedicated external transport rather than attempting local delivery ensures reliable deliverability and preserves the separation between the platform's core testing responsibilities and the orthogonal concern of messaging.

Taken together, these three integrations extend the Testing Core Engine's reach beyond its own process boundary — endowing it with borrowed cognition, with instrumented perception and action, and with a channel for trustworthy account communication — while confining each external dependency to a discrete, secured, and replaceable interface. This containment is a deliberate architectural property: it allows any single external provider to be substituted without disturbing the engine's internal logic, and it ensures that the security guarantees established at the internal interfaces are extended consistently to every boundary the platform crosses.
